# Localization

## Overview

Application localization uses `slang` and `slang_flutter`. Source translations are stored in JSON catalogs, and `slang_build_runner` generates the typed Dart API.

Supported interface languages:

- Russian (`ru`) — base locale;
- English (`en`).

When the selected locale does not contain a translation, Slang uses the base Russian locale according to `fallback_strategy: base_locale`.

## Files

```text
lib/i18n/
├── i18n.dart                # public localization export
├── language_extension.dart  # Language adapter for Flutter and Slang
├── localization_manager.dart # Slang and Intl synchronization
├── ru.i18n.json             # Russian catalog and base key structure
├── en.i18n.json             # English catalog
├── translations.g.dart      # shared generated Slang API
├── translations_ru.g.dart   # generated Russian catalog
└── translations_en.g.dart   # generated English catalog
```

Generator configuration is stored in `build.yaml`:

```yaml
slang_build_runner:
  options:
    base_locale: ru
    fallback_strategy: base_locale
    input_directory: lib/i18n
    input_file_pattern: .i18n.json
    output_directory: lib/i18n
    output_file_name: translations.g.dart
    flutter_integration: true
    locale_handling: true
    lazy: false
    enum_name: AppLocale
    class_name: Translations
    translate_var: t
    key_case: camel
    key_map_case: camel
    string_interpolation: double_braces
    timestamp: false
```

The `translations*.g.dart` files are generated by Slang and must not be edited manually.

## Catalog structure

Both catalogs must have the same structure. The Russian catalog defines the base locale, but fallback does not replace the requirement to translate each key in the English catalog.

Keys are grouped first by semantic owner and then by purpose. Flat keys with repeated prefixes are not used.

Example of the current structure:

```json
{
  "publication": {
    "complexity": {
      "easy": "Простой",
      "medium": "Средний",
      "hard": "Сложный"
    },
    "flow": {
      "backend": "Бэкенд"
    },
    "format": {
      "caseStudy": "Кейс"
    }
  },
  "search": {
    "order": {
      "relevance": "По релевантности"
    }
  }
}
```

This catalog produces typed accessors:

```dart
t.publication.complexity.easy
t.publication.flow.backend
t.publication.format.caseStudy
t.search.order.relevance
```

### Key placement rules

1. The top level identifies a domain or user-facing area: `publication`, `user`, `tracker`, `search`, or `settings`.
2. A nested object groups one kind of entity or message: `publication.type`, `user.bookmarks.types`, or `tracker.notifications`.
3. A leaf key describes its value without repeating parent names: use `publication.type.article`, not `publication.type.publicationArticle`.
4. Store an object heading under `title` or `label` when sibling properties describe the same object: `tracker.publications.title` or `summary.token.label`.
5. Group errors with their operation or entity: `company.profile.fetchFailed` or `summary.link.fetchError`.
6. Each meaning belongs to one domain. Identical text in different domains is not a reason to move it to `common`.
7. Write interpolation parameters with double braces: `{{votesCount}}`.

## Dart usage

The public import is:

```dart
import '../../i18n/i18n.dart';
```

Code that does not depend on `BuildContext` uses the global typed catalog `t`:

```dart
String get label => t.publication.type.article;
```

Widget code can use the catalog associated with its current context:

```dart
Text(context.t.tracker.publications.title)
```

When the translations object itself is required, obtain it through the provider:

```dart
final translations = Translations.of(context);
Text(translations.summary.token.label)
```

Interpolated keys are generated as functions with named parameters:

```dart
t.user.list.votes(votesCount: count)
```

## Application integration

The root `Application` wraps the app in `TranslationProvider`. This makes the Slang catalog available throughout the widget tree and allows dependent widgets to rebuild after a locale change.

The `Language` enum defines the application languages:

```dart
enum Language {
  ru,
  en;
}
```

Localization properties for `Language` are defined in `language_extension.dart`: `appLocale` maps the model to generated `AppLocale`, `locale` provides the Flutter/Intl locale, and `label` returns the localized language name. The `Language` data model itself does not depend on Flutter or Slang.

The current interface language is persisted by `LanguageRepository` in `CacheStorage` under `CacheKeys.langUI`. The `LanguageRepository.onUIChange` stream updates `SettingsCubit`. `GlobalBlocListener` then passes the selected `Language` to `LocalizationManager.setLocale`.

`LocalizationManager` synchronizes both application localization systems:

- it calls `LocaleSettings.setLocaleSync(language.appLocale)` for Slang;
- it sets `Intl.defaultLocale` from `language.locale`.

After synchronization, `GlobalBlocListener` updates the application’s localized quick actions.

Publication languages are persisted separately under `CacheKeys.langPublications`. They affect Habr request parameters and cookies but do not select the interface catalog.

## Adding and changing translations

1. Choose the semantic domain and nested key group.
2. Add the same path to `ru.i18n.json` and `en.i18n.json`.
3. For a new language, add a value to `Language`, mappings for `locale`, `appLocale`, and `label` in `LanguageExtension`, and the corresponding `.i18n.json` catalog.
4. Run code generation:

```bash
.fvm/flutter_sdk/bin/flutter pub run build_runner build --delete-conflicting-outputs
```

5. Use the generated typed accessor instead of a string key.
6. Format changed Dart files and run the analyzer:

```bash
.fvm/flutter_sdk/bin/dart format <changed-dart-files>
.fvm/flutter_sdk/bin/flutter analyze
```

## Verification

The primary localization checks are in `test/i18n/localization_test.dart`. They cover:

- correspondence between `Language` and `AppLocale`;
- error localization in the presentation layer;
- ownership of keys by semantic domains;
- catalog switching through `TranslationProvider`.

Run the localization tests with:

```bash
.fvm/flutter_sdk/bin/flutter test test/i18n/localization_test.dart
```

After changing the key structure, migrate every Dart callsite and regenerate the Slang API. Do not retain old accessors as aliases.
